# Grok Bot Pack routine: disabled release candidate

This uses the actual Grok Bot webhook routine, not the xAI model API. The Worker stores a verified `/pack to:grok` job before sending only `{ "job_id": "...", "admission": "<one-time proof>" }` to the exact operator-configured routine URL. No question, owner session, private data or seat key is included. The routine retrieves the job through its dedicated Pack connector. No proof is exposed in Pack readback.

Each wake attempt generates a random, short-lived admission proof; only its hash is persisted. The authenticated routine must bind with that exact job and proof. CAS consumes the proof once and binds the returned lease to that job. Duplicate/delayed proofs cannot bind a completed job or replace another active job. Old leases cannot read, poll, claim, release or answer another routine job. A lost bind response requires owner investigation; never rebind blindly. The proof is not a reusable seat lease, but is sensitive until consumed/expired: do not log or expose it. Routine execution history may retain its input, so the supported secure workflow must protect that history.

This prevents cross-job takeover; it does not prove external run termination. Activation remains pending secure setup, included-only billing, reviewed release and real end-to-end evidence.

Default flags are off. Admission can use a configured wake without a polling lease, but still requires the verified owner's linked Discord identity, configured guild/channel, grok seat and enabled Pack delivery. Dispatcher rechecks the dedicated key against the user store, owner link and seat stop before sending. There is one outstanding unanswered wake, not proof of one external run at a time. After a Discord receipt the next job may wake; the prior routine must stop after readback. Existing manual seats retain their binding behavior. Grok wake mode requires one-time job admission; owner stop cannot be bypassed.

CAS reservation prevents concurrent/duplicate sends. Only HTTP 202 is acknowledged; it is not a completed answer. Documented 429/503 responses retry at most three attempts; 400/401/413 are rejected. Other statuses/network ambiguity remain uncertain and block further wakes. A persisted in-flight reservation is never replayed after a crash. There are at most three wake attempts per UTC clock hour and ten per UTC calendar day, including retries. Pending jobs expire after twenty minutes. Unknown or timed-out accepted execution needs owner investigation; timeout does not prove the run ended. Existing five-minute scheduling recovers pending jobs. No new scheduler is provisioned.

Call `dd_pack_answer({lease,id:job_id,text})` with 1-1800 characters, no links/raw mentions, or `outcome:"failed"` if unable. Read the same job and report its stored delivery receipt. Only release your own unsent claim; never release or resend after reserved or uncertain delivery. Report uncertainty explicitly and stop.
